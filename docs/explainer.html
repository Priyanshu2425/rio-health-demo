From a prescription photo to a pharmacist-verified cart

A one-day demo for Rio's founders. A customer sends a photo of a prescription in a WhatsApp-style chat. Rio reads it, matches each line to a real Indian SKU, offers cheaper generics, and puts the order in front of a pharmacist who can approve it in seconds.

Why it exists

One flow, done properly

The audience is Rio's founders or hiring team. After a 90-second Loom they should think: this person understands regulated pharmacy ordering over WhatsApp, and ships end to end. So one path gets nearly all the effort: photo, cart, pharmacist review, verified. The forecast tab is a bonus, and the first thing to go if time runs out.

The compliance rule

Every prescription order is reviewed

Schedule H and H1 drugs legally need a pharmacist's check before they're dispensed, and a prescription photo almost always contains them. So confidence never decides whether a pharmacist sees an order. It decides how fast they can clear it.

TriageWhenPharmacist action
redNo SKU, drug illegible, or match score below 0.6Must edit or remove
amberMatch score below 0.85, a missing field, or any field illegibleCheck against the image
greenEverything elseOne-tap approve
Confidence is computed, never self-reported

It combines the catalog match score, field completeness and per-field legibility. An LLM's own "0.95" is uncalibrated, so it's never used. Typed orders that are all OTC (say, "dolo and ORS") skip the queue. Typed requests for Rx-only items get "please upload a prescription".

Parsing pipeline

Two narrow LLM calls, with arithmetic in code

Vision extract

One call per image, strict JSON output. Literal raw_text plus fields and an illegible flag per field.

VISION_MODEL

Candidates

Postgres pg_trgm search on brand and composition. Top 5, deterministic, under 50 ms.

no LLM

Re-rank

A cheap text-only call to pick one candidate or none, only when the top two are close.

RERANK_MODEL

Cart

Quantity, generic alternative, confidence and triage, all as pure functions with table-driven tests.

no LLM
quantity_packs = ceil(doses_per_day × duration_days ÷ pack_size) # written quantity wins if present; 1 pack plus a reason if an input is missing

All LLM calls go through OpenRouter. The model IDs are environment variables chosen by the eval, not by guessing. If the vision call fails or times out, the chat offers "Try a sample", which uses a cached parse, so the Loom never depends on a live model call.

Catalog

Real Indian SKUs, keyed by composition

Source

The Kaggle "A-Z Medicine Dataset of India" (about 250k rows), trimmed to 5–10k SKUs: the most common compositions, the cheapest brand of each, well-known brands, and a must-include list of about 150. The trimmed seed is committed, so the demo never depends on Kaggle.

composition_key

amoxycillin 500mg + clavulanic acid 125mg. Salts are normalized and sorted. SKUs with equal keys can be substituted, which is where generic alternatives and "Save ₹X" come from.

Rx-only flag

About 150 Schedule H/H1/X salts curated by hand. An SKU is Rx-only if any of its salts is on that list. It's approximate, and the README says so.

Search

Trigram similarity on brand and composition, taking the better of the two, and tolerant of spelling variants (amoxicillin/amoxycillin).

Eval

Accuracy reported by set, not blended

A model reads handwriting-style fonts far better than a real doctor's scrawl. Reporting one blended number would flatter the system, and anyone at Rio would notice.

SetSizeHow it's made
Synthetic20Rendered clinic letterheads, 2–5 lines, real brands. Degraded to look like phone photos (rotation, blur, JPEG compression, shadows). Ground truth written at generation time.
Handwritten10Written on paper by the owner in 2–3 different hands, photographed with a phone, and labelled by hand. No real patient data.
  • Headline metric: SKU match accuracy, meaning the cart line has the right composition and strength.
  • Also reported: line recall, per-field accuracy, % green (lines approved unedited), p50/p95 latency and ₹ per prescription.
  • Model comparison: 3 vision candidates on OpenRouter, ending in a table in the README.
  • H4 gate: SKU match ≥ 80% on the synthetic set.
Bonus tab

Forecast, deliberately small

The order data is synthetic: about 50 SKUs × 3 areas, 90 days, hourly. It has an evening peak, a different mix per area, and a flu-style spike injected into the last 21 days. The page says it's synthetic.

forecast = hour-of-week profile × 7-day EWMA level backtest = last 14 days, MAPE vs naive "same hour last week" reorder = max(0, ceil(next-24h forecast × 1.2 − on_hand))

One headline number, one actual-vs-forecast chart, and one reorder table with stockout rows highlighted. The story: the moving level catches the spike and the naive baseline doesn't.

TLS at the edge. No open ports on the box.

EC2 · FastAPI

localhost:8000 · Docker

API, parser, matcher, and forecast in the same process.

Neon Postgres

schema app_rio_health · pg_trgm

Catalog, orders (with images), synthetic orders, forecast runs. Its own role on the shared project; it can't read other apps' schemas.

OpenRouter

VISION_MODEL · RERANK_MODEL

Every LLM call. The key has a spend cap. 10 parses per IP per hour, 5 MB uploads.

The API hostname is one level deep because Cloudflare's free certificate covers only *.buildspacelabs.com, so api.rio.… would fail TLS.

How it gets built

Four agents on four branches, and you merge

Everything shared is frozen on main: the Pydantic contracts (with generated TypeScript types, JSON Schema and mock fixtures), the API spec, the database migration, module function signatures and Python dependencies. Each agent owns separate directories, so merges can't conflict. A contract change goes through a small chore/contracts-vN branch that you merge first.

Open questions

What's still undecided

Handwritten set. Who writes the 10 prescriptions, and are 10 enough to report a number without over-claiming?
Pharmacist UX. Is one reviewer per order right, and what does "reject" mean for the customer?
